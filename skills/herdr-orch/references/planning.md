# Plan and route responsibilities

A responsibility key names durable direction, ownership, and context. Reuse an exact responsibility lane by default. Busyness alone never justifies another lane. Separate the same responsibility only when direction, ownership, or dependency genuinely requires isolation, and record that witness in the plan and assignment.

A plan is finished only when every piece of work has an executor. Before freezing `plan.md`, list each piece with its route — yourself, a host subagent, or a responsibility lane with its profile — as `herdr_assignment route` judged it on the piece's goal (open `skill://herdr-orch/references/delegation.md` only where that verdict is undecided or you overrule it, and record the ground), and the dependencies between pieces, so that everything independent is dispatched at the freeze and runs in parallel while you do only what is yours. A piece you keep carries the rule-2 ground beside it; a piece with no executor is an unfinished plan, not a task for later. The track's measure is completion within its budget: your context is spent on judging, and where a judgment can be delegated — a review, a design fork, a measurement — delegate the judgment, judge only whether what came back is reasonable, and hand the execution to a lane.

After writing the draft `plan.md` with the user and before freezing it, decide whether to dispatch a slow-profile lane charged as its adversary — one that attacks omissions, unstated assumptions, and vulnerabilities and returns evidence-cited findings through its lane report. The decision is a trade: what the review can catch (a wrong premise, a missing piece, an interaction between pieces, a decision the user made on incomplete evidence) against what it costs (its rounds against the budget, the time before dispatch, your context spent answering it). Run it when what it can catch is worth more than what it costs; skip it when it is not. That the user approved the plan is evidence for the plan, never by itself a reason to skip — a user can decide wrongly on what they were shown. Either way, record the trade in `plan.md`. When the lane runs, answer each round with an `[ORCH Response]`, fold accepted findings into the plan, and re-engage it until a round yields no blocking findings or you record acceptance with grounds; record the lane and every finding's disposition, and route items requiring user authority through the judgment ladder.

Before dispatch, ensure the assignment states the complete goal, observable completion conditions, exact write ownership, dependencies, and user boundaries in language the worker can execute without chat history. Run the tool's preflight and accept its canonical hash; after dispatch, never rewrite the assignment — a successful add makes the file read-only, and a correction is a NEW assignment.

Four authoring rules the tool does not state where you write: `label` is 1 to 48 characters of letters, digits, `-` or `_`, beginning and ending alphanumeric, display only. `# Write ownership` bullets are one file path each, never a glob or a directory with a pattern — the tool audits only machine-readable paths, and a pattern leaves the lane unaudited. `# Goal` is at most 4096 characters; a longer specification goes into a run document pinned by hash under `# References`. A completion condition is phrased as an observable property of the work ("no function resolves routes", "the four owned files are the lane's only changes"), never as a repository-wide grep returning zero or a clean `git status`: the shared tree already carries other lanes' changes and the ORCH's own, and a legitimate remainder — a retired-key warning, a negative assertion in a test, a file another lane owns — turns such a condition into a false blocked boundary.

The assignment file and settlement block grammar is in `herdr-delegator://contract` §Assignment and settlement grammar. Profile selection belongs only in `delegation.md`.
